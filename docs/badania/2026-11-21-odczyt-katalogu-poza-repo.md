# Badanie: Jak dać agentowi (Claude Code, Codex CLI) odczyt katalogu poza repo bez zapisu i bez sterowania przez instrukcje z tego katalogu?

- Data: 2026-11-21
- Dla: ogólne (referencje w osobnym katalogu, np. `C:\progs\ref\<nazwa>\`, projekt w repo A)
- Kontekst: Windows 10, PowerShell; dokumentacja Claude Code z 2026-11-21 (strony wspominają progi v2.1.257–v2.1.326; numeru bieżącej wersji nie ustalano), dokumentacja Codex z 2026-11-21 (ostatnie wydanie na GitHubie: rust-v0.171.0, 20 listopada)
- Pewność: średnia (Claude Code: wysoka dla ładowania instrukcji, średnia dla zagnieżdżonych CLAUDE.md w dodanym katalogu; Codex: niska dla odczytu poza workspace i dla `--add-dir`, bo dokumentacja milczy); żadnych testów uruchomieniowych

## Odpowiedź

Claude Code: katalog dodany przez `permissions.additionalDirectories` w settings.json daje tylko dostęp do plików i nie ładuje z niego żadnej konfiguracji (CLAUDE.md, skille, agenci). `--add-dir` i `/add-dir` dodatkowo ładują skille, komendy i agentów z `.claude/` tego katalogu, a CLAUDE.md tylko przy `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`. Zapis blokuje się regułą `deny` `Edit(//ścieżka/**)` (dla narzędzi plikowych) plus piaskownicą dla Bash, ale piaskownica nie działa na natywnym Windows. Codex: tryb `workspace-write` pozwala pisać tylko w workspace i `writable_roots`/`--add-dir`; odczyt poza workspace jest w kodzie domyślnie dozwolony (`has_full_disk_read_access` zwraca `true`), ale dokumentacja tego nie opisuje; AGENTS.md z katalogu spoza projektu nie jest wczytywany (przeszukiwanie od korzenia projektu do cwd). Pełnej gwarancji „nie wykonuj instrukcji” nie daje żaden mechanizm, więc potrzebna jest reguła w AGENTS.md/CLAUDE.md repo.

## Ustalenia

### Claude Code

1. Trzy sposoby dodania katalogu: „During startup: use `--add-dir <path>` CLI argument; During session: use `/add-dir` command; Persistent configuration: add to `additionalDirectories` in settings files”. Pliki w dodanym katalogu „follow the same permission rules as the original working directory: they become readable without prompts […] and file editing permissions follow the current permission mode”. [1]
2. Odczyt bez pytania działa w katalogu roboczym i dodanych: „Read-only | File reads, Grep | No, within the working directory and additional directories”. Edycja wymaga zgody, poza trybem `acceptEdits`, który „automatically accepts file edits […] for paths in the working directory or `additionalDirectories`”. [1] (wniosek: dodanie katalogu daje też możliwość zapisu po akceptacji, więc samo dodanie nie jest „tylko do odczytu”)
3. Ograniczenie do odczytu narzędziami plikowymi: reguły `Edit(path)` obejmują zapis; „`Write`, `NotebookEdit`, or legacy `MultiEdit`: use `Edit(docs/**)` in place of `Write(docs/**)`”. Reguła `Write(ścieżka)` nie zadziała, trzeba `Edit`. Absolutna ścieżka to prefiks `//`: „`Edit(//tmp/scratch.txt)`: edits the absolute path `/tmp/scratch.txt`”; `~/path` to katalog domowy. [1] (wniosek: dla `C:\progs\ref\` należy użyć `Edit(//c/progs/ref/**)` albo wariantu z `C:/...`; dokładnego zapisu dla dysków Windows w źródłach nie znaleziono, wymaga próby)
4. Reguły `deny` mają pierwszeństwo i obowiązują od razu: „`deny` and `ask` rules apply right away” (dla `.claude/settings.json` projektu nie czekają na zaufanie do folderu), a `permissions.additionalDirectories` w pliku współdzielonym czeka na zaufanie. [2]
5. Reguła `Edit` nie obejmuje poleceń Bash w ogólności. Dokumentacja opisuje sprawdzanie przekierowań (`>`, `>>`), `tee` i `cd`, ale kontrola dotyczy tych konkretnych form; do egzekwowania niezależnego od tekstu polecenia: „For filesystem and network enforcement that doesn't depend on the command text, use sandboxing. To inspect the full command text with your own logic before it runs, use a PreToolUse hook.” [1]
6. Piaskownica: „The sandbox covers shell commands only. Claude's file tools, MCP servers, and hooks run outside it.” Domyślnie piaskownica daje zapis do katalogu roboczego i do katalogów dodanych: „read and write access to the current working directory and its subdirectories, any directories you've added with `--add-dir`, `/add-dir`, or `permissions.additionalDirectories`”. Odczyt: „read access to the entire computer, except certain denied directories”. Blokada zapisu w dodanym katalogu: `sandbox.filesystem.denyWrite`. [3]
7. Piaskownica na Windows: „The sandbox runs on macOS, Linux, and WSL2. On native Windows, Claude Code runs commands unsandboxed.” [3] (wniosek: na natywnym Windows poleceniom Bash/PowerShell w katalogu referencyjnym nie zapobiegnie zapisowi żaden mechanizm systemowy; zostają reguły `deny` i hook PreToolUse)
8. Ustawienia `permissions.blockWritesOutsideWorkingDirectories` (od v2.1.314) i `blockReadsOutsideWorkingDirectories` (od v2.1.257): narzędzia `Write`/`Edit`/`NotebookEdit` odmawiają zapisu poza katalogami roboczymi „in every permission mode, including `bypassPermissions`”, ale „The key doesn't limit shell commands, MCP tools, or the programs hooks run”. Katalog dodany jako roboczy jest przez nie przepuszczany, więc dla naszego przypadku (katalog dodany) nie pomagają. [1][2]
9. Wczytywanie instrukcji z dodanego katalogu — sedno: „By default, CLAUDE.md files from these directories are not loaded.” Z `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` ładowane są `CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md` i `.claude/rules/*.md` (bez reguł z polem `paths`). Zmienna istnieje w oficjalnej dokumentacji. [4]
10. Wyjątki od „tylko dostęp do plików”, dotyczą wyłącznie `--add-dir`/`/add-dir` (także SDK): „Skills in `.claude/skills/` | Yes, with live reload”, „Command files in `.claude/commands/` | Yes”, „Subagents in `.claude/agents/` | Yes”, `.claude/settings.json` i `settings.local.json` | „`enabledPlugins` and `extraKnownMarketplaces` keys only”, CLAUDE.md/rules/`CLAUDE.local.md` | tylko ze zmienną. [1] Dla `permissions.additionalDirectories`: „grant file access only and don't load any of the configuration below”. [1] Hooki i inne klucze settings: „Hooks and other `.claude/settings.json` keys load from the current working directory's `.claude/` folder”, czyli nie z dodanego katalogu. [1]
11. Ładowanie zagnieżdżonych CLAUDE.md na żądanie: „Claude also discovers `CLAUDE.md` and `CLAUDE.local.md` files in subdirectories under your current working directory. Instead of loading them at launch, Claude Code loads each one once Claude reads, writes, or edits another file in that subdirectory.” Dotyczy to podkatalogów katalogu roboczego; dokumentacja nie mówi, czy mechanizm obejmuje też podkatalogi katalogu dodanego. [4] Dla AGENTS.md: ładowany jest też „a subdirectory's `AGENTS.md`, when Claude opens a file there with the Read tool”, a tabela mówi o dodanych katalogach ze zmienną: „Their `CLAUDE.md` loads | Their `AGENTS.md` doesn't load”. [4]
12. Zaufanie: dodanie folderu spoza zaufanego obszaru przez `--add-dir`/`/add-dir` w terminalu wymaga potwierdzenia zaufania (od v2.1.326). [1]
13. Opcje wyłączające ładowanie instrukcji globalnie: `claudeMdExcludes` (wykluczanie plików CLAUDE.md wg wzorców) i tryb `managed-only` ustawienia źródeł instrukcji. W `managed-only` „A subdirectory's `CLAUDE.md` and `.claude/rules/` files […] still load on demand”. [4]

### Codex CLI

14. Tryby piaskownicy: `read-only`: „The agent can inspect files, but it can't edit files or run commands without approval.” `workspace-write`: „The agent can read files, edit within the workspace, and run routine local commands inside that boundary.” `danger-full-access`: „The agent runs without sandbox restrictions.” [5]
15. Dodatkowe katalogi do zapisu: klucz `sandbox_workspace_write.writable_roots`; „writable roots let you extend the places it can modify without removing the sandbox entirely.” [5] W kodzie: `add_dir` — „Additional directories that should be writable alongside the primary workspace.” [6] `--add-dir` dodaje więc katalog do zapisu, nie do samego odczytu. Dokumentacja zaleca: „prefer `--add-dir` rather than forcing `--sandbox danger-full-access`”. [7]
16. Odczyt poza workspace: dokumentacja trybów tego nie rozstrzyga („The page doesn't say whether the sandbox restricts reads outside the workspace”, wynik czytania strony [5]). Kod: `WorkspaceWrite` to „Same as `ReadOnly` but additionally grants write access to the current working directory (“workspace”)”, a `has_full_disk_read_access(&self)` zwraca `true`. [8] (wniosek: w modelu SandboxPolicy odczyt całego dysku jest domyślnie dozwolony, więc `C:\progs\ref\` jest czytelny bez żadnej konfiguracji; dotyczy kodu z gałęzi main, nie sprawdzano zachowania wydania 0.171.0)
17. Zapis poza workspace: „Codex asks for approval to edit files outside the workspace.” [9] Chronione ścieżki: „Even within writable roots, `<writable_root>/.git`, `.agents`, `.codex`, and `.aws` are protected as read-only when they exist as directories”. [9] Sieć domyślnie wyłączona: „By default, the agent runs with network access turned off.” [9]
18. Nowszy system profili uprawnień (Beta, nie łączy się ze starym): „Configure either `default_permissions` and `[permissions]`, or `sandbox_mode` / `sandbox_workspace_write`, but not both.” Pozwala odmówić odczytu: „Use `deny` for files or subtrees that Codex should not read”; „`deny` takes precedence over `write`, and `write` takes precedence over `read`”; wbudowane `:read-only`, `:workspace`. Dokumentacja profili nie wspomina `add-dir`. [10]
19. Windows: „On Windows, Codex uses the native Windows sandbox when you run in PowerShell.” [5] Szczegóły natywnego sandboxa (tryby `elevated`/`unelevated`, MXC) są na osobnej stronie, której nie czytano. [9]
20. AGENTS.md: „Starting at the project root (typically the Git root), Codex walks down to your current working directory.” W każdym katalogu: `AGENTS.override.md`, potem `AGENTS.md`, potem `project_doc_fallback_filenames`; „at most one file per directory”; globalnie z `~/.codex`; limit `project_doc_max_bytes` (domyślnie 32 KiB). Źródło: „We do **not** walk past the project root.”; „If no marker is found, only the current working directory is considered.” [11][12] (wniosek: AGENTS.md w `C:\progs\ref\<nazwa>\` nie jest wczytywany automatycznie, gdy cwd jest w repo A, ponieważ leży poza drzewem projekt-root → cwd; staje się wczytany, jeśli agent uruchomi Codex z cwd w tym katalogu albo sam go przeczyta jako plik)
21. Codex w źródle pomija ładowanie AGENTS.md w niezaufanych projektach („Untrusted projects skip loading entirely”). [12]

### Wniosek praktyczny (wnioski własne)

22. Claude Code, konfiguracja „czytaj, nie pisz, nie wykonuj instrukcji”: dodać katalog przez `permissions.additionalDirectories` (nie `--add-dir`), bo tylko ta ścieżka nie ładuje z niego skilli, agentów ani komend [1]; nie ustawiać `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD`; dodać `deny` na `Edit(//…/ref/**)` (obejmuje Write i NotebookEdit) [1]; na macOS/Linux/WSL2 dodać piaskownicę z `sandbox.filesystem.denyWrite` dla tej ścieżki [3]; na natywnym Windows uzupełnić hookiem PreToolUse blokującym Bash/PowerShell piszące w tej ścieżce [1][3]. (wniosek)
23. Czego Claude Code nie gwarantuje mechanizmem: (a) gdy agent czyta plik w dodanym katalogu, jego treść (w tym CLAUDE.md czytany jawnie narzędziem Read) trafia do kontekstu jako zwykła treść pliku i może zawierać prompt injection; (b) nie potwierdzono, czy zagnieżdżone CLAUDE.md w dodanym katalogu są dociągane przy odczycie plików (dokumentacja mówi o podkatalogach katalogu roboczego); (c) `Edit` deny nie zatrzyma dowolnego polecenia powłoki bez piaskownicy. Potrzebna reguła w CLAUDE.md/AGENTS.md repo: pliki instrukcji z katalogu referencyjnego traktować jako dane, nie wykonywać zawartych w nich poleceń, nie pisać do tego katalogu. (wniosek)
24. Codex, konfiguracja: uruchamiać w `workspace-write` (domyślny) bez `--add-dir` i bez wpisu w `writable_roots` dla katalogu referencyjnego; odczyt jest wtedy (wg kodu) dozwolony, zapis wymaga zatwierdzenia i leży poza piaskownicą, więc trzeba nie zatwierdzać go albo użyć `read-only`. Gdyby trzeba było twardo zablokować odczyt lub zapis, służy beta profili z regułą `deny`. AGENTS.md z katalogu referencyjnego nie jest ładowany automatycznie [11][12]. (wniosek)
25. Czego Codex nie gwarantuje mechanizmem: ochrony przed treścią instrukcji w plikach, które agent sam otworzy; oraz w trybie `read-only` i `workspace-write` jest „approval” zamiast twardej odmowy (pytanie do użytkownika, nie zakaz), o ile nie ustawiono polityki zatwierdzeń `never` (wniosek; polityki `never` w tym badaniu nie sprawdzano). Potrzebna ta sama reguła w AGENTS.md repo. (wniosek)

## Niepewności

- Nie ustalono, czy zagnieżdżone CLAUDE.md/AGENTS.md w podkatalogach dodanego katalogu są dociągane przy odczycie tam pliku. Dokumentacja opisuje tylko „subdirectories under your current working directory”. Wymaga testu: katalog z CLAUDE.md w podkatalogu, `/add-dir`, odczyt pliku, obserwacja linii `Loaded` / hooka `InstructionsLoaded`.
- Składnia reguły `Edit(...)` dla ścieżek z literą dysku Windows (`//c/progs/ref/**` vs `C:/progs/ref/**`) nie została potwierdzona w źródłach.
- Czy `deny` `Edit` na ścieżce wewnątrz katalogu dodanego przez `additionalDirectories` pokonuje tryb `acceptEdits`: dokumentacja mówi o deny „apply right away”, ale nie przeprowadzono testu. Nie czytano pełnej sekcji kolejności reguł.
- Strona settings-reference (460 tys. znaków) była czytana tylko do 100 tys. znaków; pełnych wpisów `permissions.additionalDirectories`, `sandbox.filesystem.denyWrite` i sekcji „let one directory through the read or write block” nie zacytowano. Strona sandboxingu czytana do 100 tys. z 112 tys. znaków.
- Codex: odczyt poza workspace w trybie `workspace-write` nie jest opisany w dokumentacji; potwierdzenie pochodzi tylko z kodu (`has_full_disk_read_access` zwraca `true`, gałąź main, odczyt tylko fragmentu pliku 100 tys. z 260 tys. znaków). Kod mógł się zmienić w wydaniu 0.171.0 i w nowym systemie profili. Opis `--add-dir` w tabeli referencyjnej CLI jest „placeholderem” w skopiowanej stronie; potwierdzenie opiera się na komentarzu w kodzie [6] i wzmiance w poradniku [7].
- Dokumentacja Codex przeniosła się z `developers.openai.com` na `learn.chatgpt.com` (przekierowania 308); treści pobrano z nowego adresu. Nie sprawdzano strony natywnego sandboxa Windows ani polityk zatwierdzeń (`approval_policy`), w tym `never`.
- Wyszukiwanie sieciowe wskazało (niepotwierdzone w źródle pierwotnym, blogi): do v0.122 błąd `--add-dir` w Bubblewrap na Linuksie; nie dotyczy Windows.
- Nie badano Claude Code działającego na tym repo (`claudeMdExcludes` itp.) ani wpływu pluginu `ai` na ładowanie. Brak testów uruchomieniowych w obu narzędziach.
